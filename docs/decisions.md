# Decisions

Phase 2: accounts, projects and ingestion keys.

- **Postgres 17 + Drizzle.** Migrations are generated by drizzle-kit, committed as SQL in `apps/api/drizzle`, and applied with `pnpm --filter api db:migrate`, never on boot. Services query Drizzle directly. A repository interface is added only where a second implementation exists (events).
- **Tests** run against a Testcontainers Postgres: migrations in global setup, truncate before each test, e2e files run one at a time. `pnpm check` needs Docker.
- **Passwords:** argon2id (m=19456, t=2, p=1), max 128 chars. Login failures return one generic 401. Unknown emails still verify against a dummy hash, so timing does not reveal whether an account exists.
- **Access token:** HS256 JWT, 15 min, returned in the body. Algorithm, issuer and audience are pinned on verify.
- **Refresh token:** 256-bit random value in the `rt` cookie (`HttpOnly; Secure; SameSite=Lax; Path=/v1/auth`, 30 days, sliding). Stored as a SHA-256 hash. Rotated on every use inside a row-locked transaction. Reuse of a rotated or revoked token revokes its whole family.
- **CORS:** dashboard routes allow only `DASHBOARD_ORIGIN`, with credentials. `POST /v1/events` allows any origin, because `ApiKeyGuard` checks the origin itself.
- **Ingestion keys:** `pk_` + 32 random bytes, stored as a SHA-256 hash plus an 11-character prefix. The plaintext is returned once. New keys never revoke old ones. The key is sent as `X-Api-Key` or `?key=` (for `sendBeacon`); the header wins.

Phase 3: event storage, rollups and the query API.

- **Events table** is partitioned by `RANGE (received_at)`, one partition per UTC day, named `events_pYYYYMMDD`. `received_at` is server time and the main timestamp; `client_timestamp` exists but stays null until the SDK sends one. There is no default partition, so an insert outside the created range fails instead of piling up somewhere unmanaged.
- **Partition maintenance** runs on startup and hourly: it creates today plus 7 days ahead and drops partitions whose whole range is older than 30 days. Dropping a partition is instant and leaves no dead tuples, unlike `DELETE`.
- **No DB-level deduplication.** A unique constraint on a partitioned table must include the partition key, and `received_at` differs between retries of the same event, so `(project_id, client_event_id, received_at)` would never catch a duplicate. A resent event is stored twice. Deduplication by `client_event_id` happens in the worker (Phase 4).
- **Ingestion** writes a batch as one multi-row `INSERT`, so it is stored entirely or not at all. `events.project_id` has no foreign key: the per-row check on the hot path and a cascade that would need a `project_id` index in every partition cost more than they protect. Rollups do have one, with `ON DELETE CASCADE`.
- **Hourly rollups** (`event_rollups_hourly`) hold count, rating counts, sum and a histogram per (project, metric, route, device, release, hour), unique with `NULLS NOT DISTINCT` because release can be null. Every 5 minutes a job recomputes the last 3 hours from raw events and upserts, so reruns are idempotent and late events are absorbed.
- **Histogram buckets** are `(lower, upper]` with per-metric edges in `@rum/shared` (`METRIC_BUCKET_BOUNDARIES`). Upper edges are inclusive so they agree with `rateMetric` (`value <= good` is good), and every good/poor threshold is an edge. Percentiles sum bucket arrays element-wise in SQL and interpolate linearly inside the bucket in TypeScript; percentiles are never averaged. A percentile in the open last bucket reports that bucket's lower edge.
- **Scheduled jobs** run in the worker as BullMQ job schedulers (Phase 4). Each also takes `pg_try_advisory_xact_lock` inside its transaction, so only one instance runs it and the lock cannot leak onto a pooled connection if the job throws.
- **Query API**: `GET /v1/projects/:id/metrics` and `/routes` read rollups only; `/routes/paths` and `/routes/attribution` read raw events for the last 7 days only. Day granularity uses UTC days. Paths use keyset pagination on `(percentile desc, path asc)`; each page still aggregates the whole route, keyset only makes paging stable as events arrive. Attribution uses web-vitals v5 keys: `target` for LCP and `interactionTarget` for INP.

Phase 4: queue, worker, rate limits, deduplication and cache.

- **Redis 7** (compose: AOF on, `noeviction`, which BullMQ requires) through ioredis with three kinds of connection. Request-path commands (rate limits, cache) fail fast: no offline queue, one retry, 200 ms timeout. The queue producer has no offline queue and checks the connection is `ready` before `add`, because BullMQ would otherwise wait for a reconnect and the request would hang. Workers use `maxRetriesPerRequest: null`, which BullMQ requires. `GET /ready` checks Postgres and Redis.
- **Ingestion** validates, resolves the key, enqueues one job `{ projectId, receivedAt, events }` on the `events` queue and returns 202. Jobs get 5 attempts with exponential backoff from 1 s. Completed jobs are removed; failed jobs stay 7 days and are logged (the dead-letter set). If the enqueue fails, the api inserts directly into Postgres (no deduplication on this path) and returns 202, or `503 INGESTION_UNAVAILABLE` if that insert fails too.
- **Worker** is a second entrypoint (`src/worker.ts`, `pnpm --filter api start:worker`) with the same DB and config modules. The `events` worker runs 10 jobs at a time, one multi-row INSERT each. Micro-batching across jobs is not done; see `docs/perf/README.md` for why it may be worth it. On SIGTERM it stops taking jobs and waits up to 25 s for active ones, then cuts its connection; jobs still running are retried as stalled.
- **Deduplication:** the worker drops repeated `clientEventId`s inside a job, then sends one pipeline of `SET dedup:{projectId}:{clientEventId} <jobId> NX GET EX 172800`. It inserts events whose key it just set or that already hold its own job id (an earlier attempt of the same job that crashed before committing). If the INSERT fails, it deletes those keys before rethrowing. The guarantee is at-least-once: a crash after the commit but before BullMQ records completion stores that batch twice.
- **Rate limits** are token buckets in one Lua script, using the Redis clock. Ingestion: 10 req/s per IP with a burst of 20 (checked before the key lookup), 50 req/s per key with a burst of 100. Login: 5 attempts per 15 minutes per IP and email (the email is hashed in the key, every attempt counts). Over the limit: `429 RATE_LIMITED` with `Retry-After`. Every limited response carries `RateLimit-Limit/Remaining/Reset` for the bucket closest to empty, where Reset is the time until the bucket is full. If Redis is down, ingestion lets requests through and logs a warning, and login returns `503 RATE_LIMIT_UNAVAILABLE`. The client IP comes from `req.ip`; set `TRUST_PROXY` behind a proxy. `RATE_LIMITS_ENABLED=false` exists only for load tests.
- **Cache:** `GET /metrics` and `/routes` are cache-aside, keyed by project and a hash of the parsed query, for 60 s ± 10 %. They are never invalidated, because rollups only refresh every 5 minutes. The ownership check runs before the cache. On a miss, one request takes a 5 s lock and fills the cache, and the others poll for up to 1 s before querying Postgres themselves. If Redis is down, the cache is skipped.
- **Maintenance:** rollups (every 5 min) and partition maintenance (hourly, plus once when the worker starts) are BullMQ job schedulers on a separate `maintenance` queue with concurrency 1. The rollup skips events of deleted projects; before this, a single deleted project failed the whole upsert on the rollups foreign key.

Phase 5: collector SDK.

- **`@rum/sdk`** (`packages/rum-sdk`) has one source and two tsup builds: ESM (`dist/index.js`, `initRum`) with web-vitals external, and a minified IIFE (`dist/rum.js`) that reads `data-key`, `data-endpoint`, `data-release` and `data-sample-rate` from its own script tag. `endpoint` is the API base URL; events go to `${endpoint}/v1/events?key=...`.
- **web-vitals 6, attribution build.** Each event carries an attribution summary per metric: selectors (`target`, `interactionTarget`, `largestShiftTarget`), the LCP resource URL without query or fragment, and phase durations. Raw entries, load state and interaction type are not sent.
- **Size budget is 7 KB gzipped**, checked by `pnpm size` (part of `pnpm check`). The attribution build alone is about 5.9 KB, so 6 KB was not reachable without dropping attribution.
- **Constants without zod.** `EVENT_LIMITS`, the enum value lists and the path pattern live in `@rum/shared/limits`, so the SDK can bundle them without pulling in zod. Payload types come from the schemas through `import type` and `satisfies`, so a schema change breaks the SDK build.
- **Every field is cleaned on the client** because the api rejects a whole batch for one bad event: path, route, release and attribution values are truncated to the shared limits, the route loses its query string and is dropped unless it starts with `/` and has no whitespace, and an empty release is omitted. Path, route, device type and connection type are captured once at init, because web-vitals reports per page load.
- **Sending:** batches of up to 10 events. A full batch is sent at once; the rest is flushed on `visibilitychange` to hidden (listened on `document`, which runs after web-vitals' capture listener on `window` has reported) and on `pagehide`. The body goes through `sendBeacon` as `text/plain` with the key in `?key=`, so no preflight is needed; if `sendBeacon` refuses or throws, the same request goes through `fetch` with `keepalive`. A failed batch is dropped, with no retries.
- **Sampling** is decided once per page load (`Math.random() < sampleRate`, default 1). A second `initRum` call does nothing. Without `crypto.randomUUID` (non-secure context) the SDK does not start.

Phase 6: dashboard.

- **Client-side data.** The dashboard calls the api directly with `credentials: 'include'`. The access token lives in memory only (`apps/web/lib/api.ts`). On load and on a 401 the client calls `/v1/auth/refresh` and retries once. The refresh is single-flight: concurrent 401s and React StrictMode's double effect share one request, because two refreshes with the same cookie count as reuse and revoke the session. A 401 retry skips the refresh when another request already renewed the token.
- **Rendering.** Server Components render layouts and the static shell; pages under the session gate are client components with TanStack Query. Nothing that reads the URL renders before the session resolves, so no extra Suspense boundaries are needed under Cache Components.
- **Filters live in the URL** (`metric`, `period`, `percentile`, `route`, `device`, `release`). `to` is rounded up to the next hour so `/metrics` and `/routes` hit the api cache. Periods over 7 days use day granularity. The route page takes the route template as `?route=`, not as a path segment.
- **Snippet hosting.** The dashboard serves the IIFE build at `/rum.js`; `predev`/`prebuild` build `@rum/sdk` and copy it to `apps/web/public` (ignored by git). `NEXT_PUBLIC_API_URL` sets the api base URL, baked in at build time.
- **Charts:** one uPlot component, loaded with `next/dynamic` and `ssr: false`. The x-axis spans the selected period, and the good and poor thresholds are drawn as labelled lines. Good, needs improvement and poor use one set of color tokens (`--color-good`, `--color-ni`, `--color-poor`), always shown with a text label because red and amber are hard to tell apart with deuteranopia.

## Known limitations

- **Origin can be forged outside browsers.** The allowlist only stops other websites from reusing a key copied from a page. A script can send any `Origin`, so with a public key anyone can submit events.
- Register is not rate limited.
- Ingestion still needs Postgres for the key lookup, so the queue protects against slow inserts but not against Postgres being down.
- When Redis is down, ingestion falls back to direct inserts, so those events are not deduplicated. If an enqueue fails after Redis accepted the job, the batch is stored twice.
- Dedup keys use Redis memory for 48 h of event ids. If a job runs out of retries and the last attempt also failed to delete its keys (for example because Redis was down), resending those events within 48 h is treated as a duplicate.
- The cache only hits on identical `from`/`to`, so the dashboard should send hour-aligned ranges.
- Access tokens stay valid for up to 15 minutes after logout.
- No grace period on refresh: two tabs refreshing at once count as reuse.
- Expired refresh tokens are never deleted.
- Register reveals whether an email exists (`409 EMAIL_TAKEN`).
- A deleted project's raw events stay until their partition is dropped (at most 30 days); every query is scoped to an owned project, so they are unreachable.
- Rollups are never pruned yet.
- If the worker does not run for 7 days, no partitions are created and ingestion starts failing.
- The SDK drops a batch when sending fails, and `sendBeacon` reports only that the browser queued it, so lost events are not noticed.
- The SDK reports hard page loads only; soft navigations in single-page apps are not tracked.
- The dashboard and the api must be on the same site (for example `app.example.com` and `api.example.com`), because the refresh cookie is `SameSite=Lax`.
- Release is a free-text filter: there is no endpoint that lists releases.
